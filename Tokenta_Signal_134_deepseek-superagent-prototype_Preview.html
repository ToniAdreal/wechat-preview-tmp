CASE STUDY / 案例分析

“DeepSeek Harness 团队 10 月 31 日在微信发文并开源 dsh-superagent-prototype，一个常驻团队仓库的编程助手原型，MIT 协议。它不等提问，直接监听一个 GitHub 仓库与可选的飞书群聊，经授权的成员发出请求后自行开工。”

“工作方式是两层结构。常驻的路由层读请求，为每个获批请求开一张工单，每张工单有独立的工作会话与文件夹，干完回到原对话交货，最典型的交货物是一份拉取请求。运行需要专用 GitHub 账号、Node.js 22.19 以上与 GitHub CLI 2.48 以上，只支持 github.com。”

“团队给出的合成测试里，约 300 条消息、约 20 个真实请求，超级助手的中位数完成时间为 12.4 分钟，95 分位 15.7 分钟，对照的单会话加子助手方案为 29.5 分位。代价是缓存 token 用量高得多，单次运行 2320 万，对照组 610 万到 1080 万。”

01 / ATTENTION BUDGET

“省的是注意力，不是 token”

“DeepSeek 的设计起点很实在，人一次只能跟住 3 到 5 个活跃助手会话。瓶颈不在模型写代码的速度，在人检查的带宽。超级助手的解法，是把检查点从过程收敛到结果，交货时再看拉取请求。”

“这个取舍有代价。Token 用量翻倍，换的是人不用全程盯着。注意力比算力贵的时候，这笔账划算。算力比注意力贵的时候，这笔账要重算。”

02 / RESEARCH LABEL

“研究原型，是免责也是诚实”

“仓库自述写得很直白，研究原型仅供参考，不是正式产品，代码可能有 bug，很多工程还是由编程助手自己写的。这既是免责，也是诚实。把未完成品说成未完成品，比包装成产品更可信。”

“对使用者来说，这意味着部署前必须自己审一遍。授权范围、仓库权限、飞书接入，每一项都要按自己的安全基线重设，不能照抄默认配置。”

03 / THE BASELINE

“对照组，暴露了真正的对手”

“有意思的是对照组。DeepSeek 没有拿人类工程师作比较，拿的是单会话加子助手的常规用法。超级助手赢的，是另一种助手用法，不是人。”

“这说明竞争已经变了。编程助手的赛场，从模型能力转向编排方式。谁能把多个会话管好，谁就能在同一模型上跑出更快的交付。”
