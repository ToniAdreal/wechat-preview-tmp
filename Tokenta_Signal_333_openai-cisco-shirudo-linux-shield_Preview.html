CASE STUDY / 案例分析

Shirudo 的名字来自日语，意思是盾。它是开源项目，BSD 2-Clause 许可，BPF 程序按 BSD 与 GPL 双许可。代码挂在 GitHub 的 shirudo-dev 组织下，项目主页与文档已经上线，12月15日还有一场技术深讲。

工作原理分四步。智能体先调查漏洞，写出针对性的防护，在漏洞复现测试与真实负载上验证效果，人工批准后部署到运行中的系统。防护用 eBPF 落在内核里的关键位置，不用改内核源码，不用重启。每一道防护都有密码学签名，加载前要验签，TPM 芯片留一份可核验的加载与移除记录。

公开测试只讲了两个例子。Codex 生成的防护在 Java 的 Base64 解码器上加了一道输入检查，直接挂到运行中的 Elasticsearch 进程上，攻击输入被拦下，服务没有停。另一个被挡住的是 PHP 漏洞。测试范围很小，离生产环境还有距离。

01 / WHAT TO WATCH

预发布是现在最大的限制

Shirudo 还不能直接装到生产服务器上。项目处在预发布阶段，目标机器要跑带 Shirudo 补丁的内核，硬件上也要满足官方要求。先对着兼容清单核一遍，再挑机器试。

它还会接管整台机器的 BPF 加载，只放行签过名的加载器。同一台机器上跑着的 Tetragon、Falco 或 Cilium 会起冲突。先在虚拟机里按官方快速上手指南跑通，再谈上生产。

02 / WHY IT MATTERS

智能体写内核防护，责任边界还没划清

防护的思路没有争议，争议在谁写防护。Expel 的 Marcus Hutchins 说，eBPF 做运行时缓解的潜力是真的，但让智能体写可能影响内核的规则，未必是好主意。一条写偏的防护，拦住的可能是正常流量。

OpenAI 的回答是人留一手。防护由智能体生成，部署由安全团队决定，签名与 TPM 记录让每一次加载都有据可查。模式能不能跑通，要看接下来几个月有没有真实团队在生产边缘用起来。
